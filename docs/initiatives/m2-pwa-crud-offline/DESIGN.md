## Problem Statement

M1 ships a vertical slice that creates and reads a Task on PSYKL's PWA. M2 closes the CRUD loop and stands up the local-first behavior that turns the PWA from a thin online-required UI into a real offline-capable app. Specifically, M2 delivers:

- PATCH and DELETE on the existing `Task` (M1 only ships POST and GET).
- A `completed_at` column on `Task` so the user can mark and un-mark completion.
- A client-side IndexedDB store that becomes the source of truth for UI reads.
- A sync engine that queues offline mutations and replays them when the network returns.
- A Service Worker (introduced for the first time in M2) that precaches the app shell and serves stale-while-revalidate reads.
- Last-Write-Wins conflict resolution between devices, implemented with two timestamps (client intent + server audit) and a clock-skew guard.
- The user-experience polish M1 deliberately deferred: loading skeletons, empty state, optimistic update affordances, toast surfaces for sync errors.
- Test pyramid extensions: Service Worker tested at the Component layer with real Playwright; multi-device LWW + tombstone scenarios tested via two Playwright browser contexts at E2E. **No new pyramid layers** — the 5-layer commitment from M1 holds.

M2 also opens the 30-day dogfood phase the project's product discovery depends on. Once M2 ships, the user runs PSYKL daily on the PWA for a month before M3 begins; that month is the first real product signal source.

**M2 still does NOT satisfy PRODUCT.md's MVP.** The MVP loop needs PSYKL execution and the first retrospective view, which arrive in M3 on the Apple-native clients. M2 closes CRUD and makes the PWA offline-resilient. The MVP loop arrives across M2 and M3, intentionally split.

## What Makes This Cool

The first moment a user types tasks on a phone with no signal and watches everything just work when they walk back into Wi-Fi. That's the dogfood unlock. Plus the sync-engine, Service Worker, and IDB plumbing built in M2 is **permanent infrastructure for the project's lifetime** (per Premise M2-P10) — every milestone after M2 that adds a new mutating PWA feature reuses the same operation log, the same Idempotency-Key wire format, the same LWW comparison, the same hybrid replay model. M2's investment compounds across M3, M4, M5+.

## Premises

These were established during this session. They must be agreed to before the recommended approach makes sense. Premises M2-P1 through M2-P9 were locked at session start; M2-P10 was added mid-session after a roadmap clarification. M2-P11 was added during the 2026-06-10 rebase onto `origin/main` after the M1 retrospective landed.

1. **M2-P1: Single-user multi-device, LWW forever, tombstones for deletes.** Inherits M1 Premise 8 unchanged. PSYKL never grows multi-user collaboration. Conflict-free Replicated Data Type frameworks remain out of scope for the project's lifetime. Last-Write-Wins is sufficient; tombstones (soft-deleted rows kept with `deleted_at` markers) propagate deletions across one user's devices.

2. **M2-P2: M1's Task model is the trunk; M2 evolves it with new columns.** No table rename, no split, no parallel schema. M2 adds `completed_at`, `updated_at` (client intent timeline), `server_updated_at` (server audit timeline), and `deleted_at` (tombstone marker). The PSYKL `Task.id` is still UUID v7, client-generated (M1 Decision #19) — the property that makes offline-create safe.

3. **M2-P3: The PWA's IndexedDB store is the source of truth for UI reads.** UI reads from IDB, never from the network. The network exists only for sync. This is what makes the offline-first experience instant (writes appear in the UI before any HTTP call).

4. **M2-P4 (revised mid-session): Background Sync API is available across the PWA's actual target browsers (Chromium-family).** Earlier in this session the premise read "can't rely on Background Sync because Safari." That was wrong. Per M2's narrowed PWA target surface (see Decision #54), the PWA does not target Safari in M2; iOS users get the native client in M3. Firefox falls back to on-online-event replay without harm. Background Sync is real for the dogfood surfaces.

5. **M2-P5 (revised mid-session): The sync engine is a SHARED replay module run by both the page bundle AND the Service Worker.** Earlier in this session the premise read "sync engine lives only in the bundle." That assumption was based on the wrong M2-P4. With Background Sync available on real target browsers, the hybrid model (Decision #52) gives both snappy in-tab replay AND tab-closed background replay. An IDB lock prevents concurrent replay between contexts.

6. **M2-P6: M2 is PWA-only.** iOS-native sync architecture is M3's problem. M2 makes choices that do not preclude M3 — the server stays authoritative; the client wire format is REST + JSON; M3's Swift client can reimplement the same protocol independently.

7. **M2-P7: M2 landed as `Status: DRAFT` until M1 close-out and retrospective landed.** On `origin/main`, that gate is now clear: all 6 M1 Specs shipped, `v0.1.0` was cut, and the M1 retrospective landed at `docs/retrospectives/2026-06-10-m1-bootstrap.md`. The retrospective did not invalidate M2's offline-first premises. M2 remains DRAFT only because the user must review and approve this design before execution planning proceeds.

8. **M2-P8: Every M2 DevTask PR honors the ≤10-production-behavior-source-files rule, TDD pyramid, and tests-in-same-PR per AGENTS.md.** Spec PRs aggregate DevTask diffs and carry no file limit. Exemptions from the DevTask-PR count: lockfiles, documentation files, code-generated paths listed in AGENTS.md (currently `components/service-task/drizzle/migrations/**`), and gitignored files (which never appear in diffs).

9. **M2-P9: M2 deliberately defers** scheduled background fetch (vs Background Sync — different API, periodic, requires user grant), push notifications, multi-tab coordination beyond IDB-event subscription, and conflict-resolution UI beyond a toast. ## Approaches Considered

### Approach A — Bundle-only sync engine, no Service Worker logic beyond manifest

Continue M1's "no SW" posture in M2. PWA gets IndexedDB and a sync engine, but the Service Worker is `generateSW`-mode minimal (just precaches the shell). Sync replays only when the tab is open and the page hears an `online` event.

**Rejected after M2-P10 emerged.** Cheap to build (~90 LOC for replay path), but fails the permanent-PWA case: real users will close tabs, and ops sit until they reopen and get online. Acceptable if M2 PWA were throwaway pre-iOS-native, not acceptable as a permanent surface.

### Approach B — Service-Worker-owned sync engine

All replay logic lives in `src/sw.ts`. Page enqueues, registers `sync` event, and waits. SW fires when Background Sync delivers. No page-side replay path.

**Rejected.** Background Sync events are gated by Chromium heuristics (battery, recent app usage, network quality). In-tab UX visibly lags — user creates a task while online and watches a "pending" badge for seconds-to-minutes before the SW gets its turn. Bad daily experience for the permanent-surface case M2-P10 demands.

### Approach C — Hybrid sync engine (RECOMMENDED, locked during this session)

A shared `replay` module is imported by both the page bundle and the Service Worker. The page runs replay on user-mutation enqueue, `online` event, and app focus. The SW runs replay on Background Sync `sync` events. An IDB row in a `sync_meta` store acts as a lock to prevent concurrent replay (~30 LOC for the lock dance with a 30-second stale-after timeout).

**Effort:** M (human: ~2-3 weeks / Claude Code: ~3-5 days of focused work). Sources of effort: idb integration + schema upgrade machinery; sync engine module with the FIFO replay loop + IDB lock + retry/backoff + idempotency; Service Worker with injectManifest + Background Sync registration; PWA UI refactor to read from IDB via `useSyncExternalStore`; loading/empty/error UI surfaces; multi-device E2E harness with two Playwright contexts; the M2 service-task work (PATCH, DELETE, tombstones, LWW logic, Idempotency-Key middleware).
**Risk:** Medium. The new surface area is real — IDB schemas need a migration story; the SW lifecycle has known footguns; concurrent-replay race needs a tested lock. All decisions to mitigate these are locked below.

### Approach D — Pure REST POST/PUT/DELETE without idempotency

Skip Idempotency-Key. Use PUT for upserts so retries land safely.

**Rejected.** PUT-on-upsert smears create vs update semantics; PATCH for partial-update is the M2 MILESTONE.md plan and the M3 task_intervals shape will need similar. Idempotency-Key is the lower-cost solution and is the IETF draft standard for exactly this case.

## Recommended Approach

**Approach C — Hybrid sync engine + IDB-as-source-of-truth + LWW with hybrid timestamps + tombstone deletes + Service Worker via `injectManifest`.**

Drizzle schema additions (concrete):

```ts

export const tasks = pgTable('tasks', {
  id: text('id').primaryKey(),
  userId: text('user_id').notNull(),
  title: text('title').notNull(),
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
  // New in M2:
  completedAt: timestamp('completed_at', { withTimezone: true }),
  updatedAt: timestamp('updated_at', { withTimezone: true }), // NOT NULL imposed by migration 0002 final ALTER (per Decision #56), not by schema-level annotation
  serverUpdatedAt: timestamp('server_updated_at', { withTimezone: true }).notNull().defaultNow(),
  deletedAt: timestamp('deleted_at', { withTimezone: true }),

```

`completed_at`, `updated_at`, `deleted_at` are **client-supplied** on writes. `server_updated_at` is **server-stamped** on every persist (defaultNow on INSERT; a trigger or NestJS service-layer setter on UPDATE). The Zod schemas in `packages/shared-types/src/schemas/` are extended to reflect the new shape; `nestjs-zod` DTOs and the emitted OpenAPI document follow automatically (per M1 Decision #12).

### Migration

New Drizzle migration file: `components/service-task/drizzle/migrations/0002_m2_task_evolution.sql` (or whatever drizzle-kit names it). The migration applies in three SQL statements (per Decision #56):

1. **ALTER ADD COLUMN (nullable):** `updated_at`, `server_updated_at NOT NULL DEFAULT now()`, `completed_at`, `deleted_at`. `server_updated_at` is stamped at migration-run time for existing rows (acceptable as audit timeline; LWW comparison uses `updated_at`, not server time).
2. **UPDATE backfill:** `UPDATE tasks SET updated_at = created_at WHERE updated_at IS NULL;`. Preserves intent timeline — existing M1 rows look like "never edited since create" rather than "edited at deploy time."
3. **ALTER SET NOT NULL:** `ALTER COLUMN updated_at SET NOT NULL`. Closes the schema contract.

`completed_at` and `deleted_at` stay null on existing rows. Integration test in Spec M2-1 (DevTask M2-1) verifies the migration applies cleanly against a seeded M1-shape table.

### M2 service-task API surface

```
POST   /tasks                    (M1, extended: now requires updated_at in body)
GET    /tasks                    (M1, extended: returns new columns; filters deleted_at IS NULL by default)
GET    /tasks?include_deleted=1  (NEW: returns tombstones for sync engine pull)
PATCH  /tasks/:id                (NEW: partial update with LWW guard)
DELETE /tasks/:id                (NEW: soft-delete; sets deleted_at to client-supplied value)
```

All mutating verbs (`POST`, `PATCH`, `DELETE`) require the `Idempotency-Key` HTTP header. Server stores idempotency records keyed by `(user_id, key)` in a new `idempotency` table with a 24-hour TTL. Duplicate `Idempotency-Key` within TTL replays the cached response without re-applying the write. See Decision #41 for the wire detail.

### Sync queue wire format (one PATCH example)

```
PATCH /tasks/T_XYZ
Headers:
  X-User-Id:        local
  Idempotency-Key:  01HXXX...           ← UUID v7 op_id, client-generated
  Content-Type:     application/json
Body:
  {
    "title":        "Buy oat milk",
    "updated_at":   "2026-05-22T14:00:03Z"   ← client intent timestamp
  }

Server logic:
  1. Check idempotency table for (user_id, Idempotency-Key). If hit + within TTL,
     return cached response without applying write.
  2. Read current row. Compare body.updated_at against row.updated_at.
     - If body.updated_at > row.updated_at + skew_clamp: apply (clamping if needed).
     - If body.updated_at ≤ row.updated_at: stale write. Return 200 with current
       row state. Client reconciles by replacing its IDB row.
     - If body.updated_at > server.now() + 5 minutes (future skew): clamp to
       server.now() before write.
  3. On write, set server_updated_at = server.now().
  4. Persist idempotency row with the response body, expires_at = now() + 24h.
  5. Return the row.
```

## What gets deferred to M3+

For clarity (M3 will get its own design doc):

- **Apple-native clients** (iOS, iPadOS, macOS). M3.
- **PSYKL execution and task_intervals table.** Time-tracking via multiple start/stop intervals per task is the M3 product surface. The sync-engine plumbing from M2 (operation log, Idempotency-Key, LWW timestamps, replay module) is designed to absorb intervals as a new op type and a new IDB store without architectural change.
- **Energy retrospectives.** M3 product differentiator. Queries client-time `completed_at` and (M3) interval `started_at`/`stopped_at`.
- **Push notifications.** Whenever the product needs them (M5+ likely).
- **Scheduled background fetch** (`PeriodicBackgroundSync`). Different API from Background Sync. Requires user grant. Defer until a feature demands it.
- **Multi-tab coordination beyond BroadcastChannel-based IDB invalidation.** If multi-tab editing becomes a real workflow, revisit.
- **Conflict-resolution UI.** LWW silently wins. No banner, no merge view. Revisit only if M3 dogfood surfaces conflicts that LWW handled wrong.
- **Toxiproxy chaos overlay.** Realistic latency/jitter/packet-loss simulation. Parked at M5+ if network-fidelity testing matters.
- **`failed_ops` inspector UI.** Store exists in M2 as a debug breadcrumb only. Surface UI when real users hit failures.
