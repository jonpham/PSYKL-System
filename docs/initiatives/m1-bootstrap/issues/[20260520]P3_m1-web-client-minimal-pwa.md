# 20260520 - M1 Spec 3: web_client minimal PWA

> Pre-implementation feature/issue doc. Once all DevTasks for this Spec merge, this doc moves to `docs/features/` as the completion record. Use as the body of a GitHub Issue.

## User Story

As a **user**, I want to be able to **open the PWA, type a task title, click create, and see the new task appear in the list** so that **PSYKL-System has a working end-to-end frontend that exercises the full architecture (PWA → API → pglite → back) and proves the dogfood loop on the web surface before Spec 4 boxes it up in Docker Compose**.

## Features (DevTasks composing this Spec)

1. **DevTask 5 — PWA shell.** Vite + React (SPA mode) scaffold, app shell, `vite-plugin-pwa` Web App Manifest, base Unit-layer tests for the shell. Independent of Spec 2 (no API contract dependency yet). ~9 files. [Sub-Issue TBD]
2. **DevTask 6 — Task UI.** Create input + list view rendering PSYKL `Task` records, `openapi-fetch` API client + generated types from `openapi-typescript` (consuming the emitted `openapi.json` from `service-task`'s build per Decision #12), Component-layer tests using Mock Service Worker (MSW, per Decision #33) to stub the `service-task` HTTP boundary. **Depends on DevTask 3 of Spec 2** for the `openapi.json` artifact; may use hand-written stub types as a transient measure during parallel development, but final merge must follow DevTask 3. ~7 files. [Sub-Issue TBD]

## Verification Steps

**Associated E2E test:** end-to-end via Playwright lands in Spec 5; this Spec is verified via Component-layer tests (real UI + MSW-stubbed back-end) and manual smoke-test against the real `service-task` from Spec 2.

**Manual verification:**

_Setup / Preconditions_
- Spec 1 and Spec 2 complete and merged.
- `service-task` running locally on `http://localhost:3000` (`pnpm --filter service-task dev`).
- `web_client` env `VITE_API_URL=http://localhost:3000` configured.

_Steps_
1. `pnpm --filter web_client dev` starts the Vite dev server on `:5173`.
2. Open `http://localhost:5173` in a browser. Page loads with the PSYKL app shell (logo or title, no console errors).
3. Open DevTools → Application tab → Manifest. Confirm the Web App Manifest loads (name, icons, theme color) — the PWA is installable.
4. The page shows an empty task list (or empty state) and an input field with a "Create" button.
5. Type "first task from PWA" into the input. Click "Create".
6. The new task appears in the list, with title and a relative timestamp.
7. Refresh the page. The task is still there (persisted to pglite via service-task).
8. Open the Network tab; create another task. Confirm: one `POST /tasks` request with `X-User-Id: local` header and `Content-Type: application/json`, response 201; one `GET /tasks` request, response 200 with array including both tasks.
9. Confirm no CORS errors in the console.

_Expectation_
A minimal PWA that creates and lists PSYKL `Task` records via the real `service-task` API. Type-safe end-to-end (no hand-coded request/response shapes — all derived from the emitted `openapi.json`). Installable as a PWA on desktop and mobile, even though the offline service worker is M2 work.

## Design Decisions

- **#3** PWA framework: Vite + React (SPA mode) + `vite-plugin-pwa`.
- **#11** Test file locations: Unit + Component tests colocated next to source; E2E lives in `e2e/` at repo root (not in this Spec).
- **#12** OpenAPI artifact path + build order: `web_client` runs `pnpm --filter web_client codegen` to invoke `openapi-typescript components/service-task/openapi.json --output src/api/types.ts`. Both `openapi.json` and `src/api/types.ts` are gitignored; CI regenerates on every PR.
- **#14** Port `:5173` for the Vite dev server.
- **#15** CORS posture: `service-task` allows `Origin: http://localhost:5173`; `VITE_API_URL` env var defaults to `http://localhost:3000`.
- **#22** No Integration test layer in `web_client` for M1 (no in-process database or middleware boundary that warrants Integration tests; Unit + Component + E2E only).
- **#33** Component-test back-end stub: Mock Service Worker (MSW) intercepting `fetch` at the HTTP boundary.

## Architecture Decisions (ADR)

- **ADR-M1-009:** Vite + React in SPA mode chosen over Next.js / Remix / SvelteKit specifically to avoid server-component-blended frameworks (per DESIGN.md Premise 4). The PWA is a clean static app served by nginx in production (Decision #21), not a Node server. See Decisions #3, Premise 4.
- **ADR-M1-010:** Service worker and offline cache deferred to M2. M1 ships an installable manifest only — the PWA is "online-required" for M1. Offline-first sync engine is a real M2 design question, not an M1 deliverable. See DESIGN.md "M1 PWA is online-required."
- **ADR-M1-011:** MSW (Mock Service Worker) chosen as the Component-test back-end stub over manual `fetch` mocks because it operates at the HTTP boundary (closest to "stubbed back-end"), reusable across Unit and Component layers, doesn't require mocking the `openapi-fetch` client internals. See Decision #33.
- **ADR-M1-012:** Type safety end-to-end via generated `openapi-typescript` types consumed by `openapi-fetch`. Breaking changes in the Zod source schemas → breaking changes in the emitted `openapi.json` → breaking changes in the generated `types.ts` → `tsc` failure in `web_client`. The contract is enforced by the TypeScript compiler. See Decision #12.
