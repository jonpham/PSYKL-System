# Design: M1 Bootstrap — Vertical Slice + Test Pyramid

> Generated by `/office-hours` (gstack) on 2026-05-20.
> This document captures the M1 initiative scope. M2 and M3+ are sketched as roadmap context only.

## Problem Statement

PSYKL-System has a product brief ([`docs/PRODUCT.md`](../../PRODUCT.md)) and three empty scaffolded components (`components/ios_client`, `components/web_client`, `components/service-task`). Before any product feature can be discovered or validated, the project needs:

- A working repository setup with end-to-end wiring across the chosen surfaces and the backend.
- A test pyramid established at all five layers (unit, integration, component, contract, end-to-end) so Test-Driven Development (TDD = writing failing tests before implementation) is the working norm from day one.
- A trained agentic workflow loop — gstack for initiative planning, superpowers for spec planning, executor for atomic commits, feature-doc consolidation on merge — exercised on a real (if minimal) feature.
- Infrastructure (Docker Compose, Continuous Integration / Continuous Deployment = automated build-test-publish pipelines) standing so M2+ doesn't have to revisit it.

M1 explicitly is **not** about discovering the product. That work belongs to M3+. M1 proves the architecture and the development style.

## What Makes This Cool

The "whoa" of PSYKL-System lives downstream (energy-aware retrospectives, adaptive PSYKL-boundary coaching, time-independent planning), but M1 has its own quiet win: **shipping a real vertical slice with a complete test pyramid from the first PR**, on a monorepo with subtree mirroring, with the agentic workflow loop trained against real (not throwaway) domain code. That foundation is what lets M2+ move fast without the usual "we'll add tests later" decay.

## Constraints

- **Monorepo with subtree-mirrored components.** Source of truth is this monorepo. `components/web_client` and `components/service-task` get pushed to standalone upstream repos via `git subtree split` after merge.
- **PWA-offline-first + service-task is the architecture.** No Next.js-style server/client blending. Clean PWA (Progressive Web App = installable web app that works offline) + clean Application Programming Interface (API).
- **No Apple-native client in M1.** iOS / iPadOS / macOS native clients arrive in M3+.
- **Single local user, hardcoded `user_id`.** Real authentication and login UI deferred to M4+ (see Premise 7).
- **Hard limit: ≤10 files changed per Pull Request (PR).** Per AGENTS.md. Specs must be designed to fit this.
- **TDD is a working-agreement rule, not a project preference.** Tests-first ordering in every spec at the appropriate pyramid layers.

## Premises

The following premises were established during the `/office-hours` session and must be agreed to before the recommended approach makes sense:

1. **Differentiator = retrospective-driven insight + adaptive PSYKL-boundary coaching.** Tasks do not require upfront energy tags. After cycles complete, retrospectives aggregate completions and surface patterns. At each PSYKL boundary (user marks complete / user pauses for fatigue / countdown timer expires), the app suggests one of: take a break, next task, recharge activity, or a known-higher-energy task. Energy is emergent from history, not user data entry.
2. **Time-independence is a soft preference, applied selectively.** Countdown timers exist (default 25-minute PSYKL, user-tunable — "psychological work cycle"). Retrospective views use calendar grids — familiar UI, not novel. The "anti-clock" stance shows up in the planning UI (no scheduled clock times for tasks), not in the execution UI.
3. **PWA-offline-first + `service-task` is Milestone 1's architecture. Apple-native is Milestone 3+ (separate).** Concurrent surface development explicitly ruled out for now to avoid tangling iOS learning with product discovery.
4. **App-paradigm separation.** PWA is fully usable offline with local-first persistence; `service-task` is a standalone API for sync + cross-device retrospectives. No server/client framework blending.
5. **Aesthetic naming is decoupled from the data model.** Code uses neutral terms (`cycle`, `task`, `period`); the UI has a configurable term-map (default theme: celestial — PSYKL, Earth, Moon, HelioArc, Sun). Theme can change without code churn.
6. **OSS adoption is downstream of dogfood.** Public repo + decent README in M1. No roadmap voting, no contribution funnel until the user has used PSYKL daily for a month.
7. **Every persisted record carries `user_id` from the first schema migration.** PWA and API enforce `user_id` matching on every request. In M1 and M2 the value is hardcoded to a single local user. Real auth/login slots in at M4+ without a data migration.

## Approaches Considered

### Approach A — Ping vertical slice (rejected after discussion)

A minimal `Ping` record with `(id, user_id, created_at)` traveling PWA → API → database → back. Throwaway scaffolding.

**Rejected because:** the schema is structurally identical to a minimal `Task`. Calling it `Ping` and throwing it away wastes the test patterns and forces a rewrite in M2.

### Approach B — Minimal Task vertical slice (recommended)

The same vertical slice as A, but the resource is `Task` from day one. M1 ships Create + Read on `Task` with a `title`; M2 extends the same table with Update + Delete + `completed_at`. No throwaway code; the data model evolves incrementally.

**Effort:** M (human: ~1-2 weeks / Claude Code: ~2-4 hours of focused work)
**Risk:** Low. Scope is small and well-bounded; the line between M1 and M2 is "Create+Read" vs "Create+Read+Update+Delete + status."

### Approach C — Pure infrastructure, no feature (rejected)

Continuous Integration / Continuous Deployment + Docker + monorepo + subtree workflow + docs templates only. Placeholder routes and components, no HyperText Transfer Protocol (HTTP) call between client and server.

**Rejected because:** does not exercise the architecture or the agentic workflow loop on real domain code. Wiring bugs would surface in M2 instead of M1, defeating the bootstrap purpose.

## Recommended Approach

**Approach B — Minimal Task vertical slice with full test pyramid.**

### M1 Task data model

```
Task {
  id          UUID                       -- Universally Unique Identifier
  user_id     string  (= "local" in M1)
  title       string  (required, 1..200 chars)
  created_at  timestamp
}
```

### M1 deliverables

**Repository foundation:**
- Monorepo workspace set up (package manager and workspace tooling decided in spec).
- `packages/shared-types` package exporting `Task`, `TaskInput`, `TaskResponse` types consumed by both PWA and API.
- `components/web_client/`: minimal PWA shell, installable, offline-capable, calls the API.
- `components/service-task/`: minimal API with `POST /tasks` and `GET /tasks`, SQLite persistence, `user_id` middleware enforcing the hardcoded `"local"` value.
- Docker Compose for local stack (PWA + API + DB in one `docker compose up`).
- CI pipeline running lint + test + build on every PR.
- Subtree-sync GitHub Action pushing `components/*` to upstream mirrors after merge to `main`.

**Test pyramid (all five layers green before M1 closes):**

| Layer | Tooling (proposed) | M1 acceptance example |
|-------|--------------------|----------------------|
| Unit | Vitest | `formatTaskTimestamp(date)` returns expected ISO string |
| Integration | Vitest + in-memory SQLite | `POST /tasks` writes row; `GET /tasks` returns user's tasks only; `user_id` mismatch rejected |
| Component | Testing Library | `<TaskList tasks={[...]} />` renders titles + timestamps in isolation |
| Contract | Shared TypeScript types | API response type matches PWA expected type; breaking changes fail the build |
| End-to-end (E2E) | Playwright | PWA loads in headless browser, user types a title, clicks create, sees the task appear in the list |

**Documentation & workflow training:**
- The full gstack → superpowers loop is exercised on M1:
  - `/office-hours` produces this design doc (✅ in progress).
  - `gstack` initiative artifacts retained under `docs/initiatives/m1-bootstrap/`.
  - `superpowers` writes spec(s) under `docs/specs/m1-bootstrap/` (one per atomic-PR-sized slice).
  - Executor commits each task atomically per AGENTS.md.
  - On completion, a feature doc is written to `docs/features/` consolidating the M1 outcome.
- README updated with quickstart (`docker compose up`).
- `CHANGELOG.md` opened with a v0.1.0 entry.

## What gets deferred to M2

- `completed_at` column and migration.
- Loading states, empty states, optimistic updates, real user-experience polish.
- The PWA's offline-first sync engine (M1 may be online-required for simplicity; offline-first is a real M2 question).

## What gets deferred to M3+

- Apple-native clients (iOS, iPadOS, macOS) — separate milestone, learned-by-doing.
- Energy retrospectives and PSYKL-boundary coaching (the real product differentiator).
- Themed term-map / configurable UI vocabulary.
- Multi-user authentication, login, homelab multi-instance support (M4+).
- Server-side vs client-side retro aggregation decision (post-M3 — parked).

## Open Questions

These do not block M1 from starting but should be resolved during M1 spec planning:

1. **Package manager + workspace tooling.** `pnpm` + workspaces? `bun` + workspaces? Turborepo on top? To be picked during the M1 superpowers spec.
2. **API framework for `service-task`.** Hono, Fastify, NestJS, Express, or something else. Picked during spec planning — `service-task` is a downstream subtree mirror, so the choice is local to that component.
3. **PWA framework for `web_client`.** Vite + React, Vite + Vue, SvelteKit (in single-page-app mode), SolidStart, etc. Constraint: must produce a clean PWA, not a server-component-blended framework.
4. **Database choice.** SQLite is the obvious M1 pick (zero-ops, in-process). Migration story for M3+ multi-device sync is a future-Jonathan problem.
5. **Term-map / theme architecture.** Decoupling neutral data-model terms from UI labels can be done with a simple translation function or a full i18n library. M3+ decision; just note the seam now.

## Success Criteria

M1 is **done** when:

- `docker compose up` from a fresh clone produces a running PWA at a local URL with a working API and persistent SQLite.
- A user can create a Task with a title via the PWA and see it appear in the list after a refresh.
- All five test pyramid layers have at least one passing test exercising real behavior (not stubs).
- CI pipeline runs the full test pyramid on every PR and blocks merge on failure.
- Subtree-sync push runs on merge to `main` and successfully pushes to the configured upstream component repos.
- A feature doc summarizing M1 is committed to `docs/features/` following the AGENTS.md template.
- A retrospective in conversation surfaces what worked and what didn't in the agentic workflow loop — input to refining AGENTS.md before M2.

## Distribution Plan

- **Repository:** GitHub public repo at `jonpham/PSYKL-System` (already exists).
- **Container images:** built in CI; published to GitHub Container Registry on tagged releases (decision: `v0.1.0` ships M1).
- **Local dev distribution:** `docker compose up` from cloned repo.
