## Problem Statement

M2 shipped a technically excellent offline-first todo list — IndexedDB source of truth, sync queue, background sync, multi-device end-to-end coverage — wrapped around a **rudimentary** task experience. The PWA has four UI components (`TaskCreateForm`, `TaskList`, `Toast`, `VersionFooter`) and a flat, single, unordered list of title-only tasks.

The operator's words: _"the ToDo use cases and UX is very rudimentary and I want to replicate/clone an Apple Reminders like experience before adding new use cases such as PSYKL loops and daily task planning."_

So the gap is not sync, and not the differentiator. It is that the app is not yet a good place to keep tasks, which makes it a poor foundation for everything after.

## What Makes This Cool

Not the feature list — Apple Reminders already exists. Two things:

1. **It's the substrate for the differentiator.** PSYKL sessions attach to tasks. A task model that only has a title can't support "tasks of type X land in low-energy windows"; a task model with lists and tags can. Every structural feature here is also a future retrospective dimension.
2. **Offline-first makes the boring features interesting again.** Manual drag-to-reorder is a solved problem in a server-backed app and a genuinely hard one in an offline, multi-device app. Getting it right — see the fractional-index decision below — is the kind of problem that only shows up because M2 was built properly.

## Constraints

- **Single-user, multi-device, siloed.** No collaboration, ever (`docs/PRODUCT.md` → Sync and Sharing Model). No shared lists, no assignees, no comments — a large fraction of Apple Reminders is therefore out of scope by definition.
- **PWA is the exploration client.** No native client work in this milestone.
- **Everything must survive offline.** Any new entity has to round-trip through the sync queue and reconcile under LWW.
- **The five-layer test pyramid holds** (`AGENTS.md` → Test Discipline). TDD ordering is mandatory; tests ship in the same pull request as the behavior.
- **Deploy target is unchanged** — robin/k3s via ArgoCD, semver image pins.

## Premises

Agreed during the session. P2 was corrected by the operator; the correction is recorded rather than the original.

**P1 — This milestone is todo experience, not the PSYKL loop.** No timers, cycles, or breaks are built here. The `psykl-loop` milestone follows this one.

**P2 — Dates are facts about a task, never a plan for your attention.** A task may carry a due date, and a time when the deadline genuinely has one (a form closes at 5pm). The app never sends a notification and never asks what time you intend to work on something. Recurrence is **not** Apple's repeat rules; the eventual mechanism is **template tasks that spawn instances**, deferred to a later milestone, but the model must not preclude it.

> This is a refinement of `docs/PRODUCT.md`'s anti-clock stance, not a reversal. The product rejects clock-time scheduling of future work. A deadline is a constraint on the task; a schedule is a claim on your attention. Reminders conflates them. PSYKL does not.

**P3 — One feature per pull request, validated by real use before the next starts.** Each feature merges, deploys to robin, and gets lived with. If use says the feature is wrong, it changes or comes out before anything stacks on top of it. Subtasks specifically are **not built** until lists and sections have been used and the operator can say whether nesting is still wanted.

**P4 — Structural features cost far more than they look.** Notes, priority, and interaction polish are one column or zero columns. Lists, sections, and ordering change the Postgres schema, the IndexedDB store, and the sync queue simultaneously.

**P5 — Do not make PSYKL sessions harder to attach later.** A session record points at a task. Keep task identity stable and singular. Low bar, stated so it doesn't get violated by accident.

## Architectural Risks

### 1. The sync queue is task-shaped

`components/web_client/src/db/idb.types.ts:9` defines `SyncQueueEntry` with a literal `task_id` field; both `sync_queue` and `failed_ops` index on it, and `op` is typed `'create' | 'patch' | 'delete'`. The coupling continues through `components/web_client/src/sync/replay.ts`, which treats successful replay responses as `Task` rows and writes them back through `putTask`, and `components/web_client/src/sync/replay.transport.ts`, which routes every queued operation to `/tasks` endpoints. Lists are a second syncable entity — created, renamed, and deleted offline — so the queue must become entity-agnostic (`entity_type` + `entity_id`) before any structural feature lands.

This is the keystone of the milestone. It is also exactly what the `psykl-loop` milestone needs for its session entity, so the cost is paid once and used twice (P5, discharged rather than merely respected). The implementation must cover the full path: IndexedDB schema versioning and migration, queue and failed-operation indexes, replay dispatch by entity type, response handling per entity store, generated OpenAPI client types, and server endpoints for each new syncable entity.

### 2. Manual reorder conflicts silently under LWW

Reorder on device A and on device B while both are offline, and LWW does not merge intent — it compares row timestamps. With integer indexes, a single reorder often renumbers many tasks, so later patches from one device can overwrite earlier position patches from another and produce lost ordering intent, duplicate or sparse positions, or a surprising hybrid order. A user losing a hand-arranged list is a bad, memorable bug, and it is invisible until it happens.

**Decision: fractional positions, not integer indexes.** Inserting between `1.0` and `2.0` writes `1.5`, so a reorder touches one row instead of renumbering the list, and concurrent reorders in different regions of the list do not collide. Decided now, before the feature is built, because retrofitting it means a migration over live data.

This does **not** make ordering conflict-free. Concurrent moves of the same task, or moves that choose the same gap, still resolve by LWW. The design goal is to shrink the conflict surface from "many rows per reorder" to "usually one row per reorder," then test the remaining conflict cases explicitly.

### 3. Sections may not need to be an entity

A section could be a real row (`sections` table, `task.section_id`) or a grouping value on the task. The former is more faithful to Reminders; the latter avoids a second structural entity. Deferred to the spec pass, flagged so it is decided deliberately.

## Approaches Considered

### Approach A: Cheap wins first

Ship everything that touches no schema — swipes, density, animation, inline edit — then single-column additions (notes, priority, due date). Lists, sections, and ordering last.

- **Effort:** M (human: ~2-3 weeks / Claude Code: ~2-3 sessions) · **Risk:** Low
- **Pros:** Something feels better within a day; no migration; establishes the ship-one-thing rhythm cheaply.
- **Cons:** Polishes a flat single list — the most toy-like property survives longest. Row layout is reworked when sections arrive, so some polish is done twice.

### Approach B: Structure first

Generalize the sync queue, then lists → sections → ordering; then detail columns; then polish last, on a layout that has stopped moving.

- **Effort:** L (human: ~3-4 weeks / Claude Code: ~3-4 sessions) · **Risk:** Medium
- **Pros:** Closes the largest gap first. Polish lands once, on final layout. Pays for the `psykl-loop` session entity's sync needs at the same time.
- **Cons:** Slowest to a felt improvement. Front-loads the fractional-index problem. Two or three pull requests before the app feels different.

### Approach C: Slice by annoyance

Order by the moments that actually irritate the operator in daily use; each slice cuts across polish, detail, and structure together.

- **Effort:** M-L (human: ~3 weeks / Claude Code: ~3 sessions) · **Risk:** Medium-High
- **Pros:** Every increment is validated by a real annoyance. Most likely to land somewhere Apple Reminders isn't.
- **Cons:** Schema churn — one slice needs half of lists, the next needs the other half. Hardest to keep the test pyramid green across partial models.

## Recommended Approach

**Approach B — structure first.** Selected by the operator.

The reasoning runs against the usual instinct to do cheap things first. The sync queue is hardcoded to tasks, and every structural feature plus the future PSYKL session needs it generalized. Doing that once, early, makes everything afterwards additive. Polishing rows before knowing whether rows nest is work done twice.

**Sequence:**

1. Generalize the sync queue to arbitrary entities as the enabling work for **Lists**
2. **Sections**
3. **Manual ordering** (fractional positions)
4. **Notes / priority / due date**
5. **Swipes / density / animation**
6. **Tags**, then **search**

Each user-visible feature is one pull request, deployed and lived with before the next starts (P3). Required enabling work may ride in the same pull request only when the feature cannot exist without it; otherwise it is split into its own non-user-visible infrastructure pull request with the same test bar.

## Open Questions

1. **Sections: entity or grouping value?** Decide during the spec pass (Risk 3).
2. **Does the generalized sync queue migrate existing queued entries, or drain first?** A user with pending offline writes at upgrade time must not lose them.
3. **What is the default list?** Reminders has an inbox concept; a flat list has no home. Existing tasks need somewhere to go at migration.
4. **Does tag design need to anticipate the retrospective?** Tags eventually power "tasks of type X." Whether that constrains tag shape now is unresolved.
5. **What is the fractional-position representation?** The spec pass must choose the persisted type and rebalance rule. The decision is fractional positions over integer indexes; it does not yet choose Postgres `numeric`, fixed-width decimal strings, lexicographic rank strings, precision limits, or compaction behavior.
6. **Milestone rename mechanics.** This design supersedes the `psykl-loop` milestone doc committed earlier today in `c0d8759`; that scope becomes the _next_ milestone. See Next Steps.

## Success Criteria

- The operator prefers PSYKL to Apple Reminders for their own daily task capture — the honest bar, since they are the user.
- A hand-arranged list survives a concurrent reorder on two offline devices with no lost arrangement (tested, not assumed).
- Every shipped feature has been used for real before the next one starts; at least one feature is changed or removed as a result of that use. Zero such changes means P3 is being performed rather than practiced.
- Five-layer pyramid green on every pull request; every user-visible behavior carries an end-to-end test whose title reads as a user story.

## Appendix: PSYKL loop specification (for the next milestone)

Captured during this session; belongs to the `psykl-loop` milestone, recorded here so it is not lost.

**A PSYKL is a fixed-period event, started when the user begins a task.** It takes over the app and shows a focused countdown.

```
task tapped ──▶ WORK (fixed period, full screen)
                 ├── "mark completed" ──▶ session ends, task done
                 ├── "pause task"      ──▶ session ends (paused)
                 └── time elapses      ──▶ BREAK (fixed period)
                                             └── elapses ──▶ "Continue?" / "Do Something Else"
```

**Data model:** `Task ──1:N──▶ PSYKL session`. A session is one start/stop event — the periods during which the user worked on that task. Pausing **ends** the session; a task accumulates many sessions over its life, as real work does.

Two consequences worth carrying forward:

- **Sessions are immutable append-only events**, not mutable rows. They need none of M2's LWW machinery — two devices appending sessions cannot conflict. This is the opposite of the assumption in the superseded milestone doc.
- **The loop is deterministic in v1.** "Take a fixed break" is a rule, not a history-informed suggestion. `docs/PRODUCT.md` promises adaptive coaching at PSYKL boundaries; that requires history which does not exist yet. Ship the mechanical loop, accumulate sessions, design coaching against real data.

**Retrospective views** — all three eventually wanted, sequenced by when they can say anything true:

| View               | Data needed before it is honest |
| ------------------ | ------------------------------- |
| Time-on-task       | one session                     |
| Today's timeline   | one day                         |
| Cross-day patterns | several weeks                   |
