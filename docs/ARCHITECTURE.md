# Architecture

This document records durable architecture decisions that survive beyond individual initiative and spec documents.

## M1 Bootstrap Architecture

M1 establishes a TypeScript monorepo with independently deployable system components under `components/` and shared packages under `packages/`. The monorepo remains the source of truth; component repositories are downstream mirrors managed later by subtree automation.

### Workspace And Tooling

- Package management uses pnpm with `pnpm-workspace.yaml`.
- Node is pinned to 24 LTS through `.nvmrc` and `engines.node`.
- pnpm is pinned through the root `packageManager` field.
- `.npmrc` sets `engine-strict=true` so version drift fails at install time.
- Static Analysis uses ESLint flat config and Prettier from the repository root. Workspace packages expose `lint`, `format:check`, and `typecheck` scripts so CI can run recursive checks consistently.

### Contract And Schema Model

`packages/shared-types` is the schema source of truth for the initial API surface. It defines Zod schemas for the PSYKL `Task` data-model entity and derives TypeScript types from those schemas.

Generated artifacts remain out of source control:

- `packages/shared-types/dist/` is generated by package build.
- `components/service-task/openapi.json` is generated by `service-task` from shared Zod schemas.
- Future client API types are generated from the OpenAPI artifact.

This makes the source schemas authoritative while still giving service and client components generated artifacts at build time.

### service-task Component

`components/service-task` is a NestJS REST API component. M1 exposes:

- `POST /tasks`
- `GET /tasks`

The service is organized around a `TaskModule`, `TaskController`, and `TaskService`. `TaskService` owns domain behavior for the M1 `Task` entity:

- Generate UUID v7 identifiers app-side.
- Insert Tasks through Drizzle ORM.
- Query Tasks scoped by `user_id`.
- Map persistence rows into Zod-derived response shapes.

### Persistence

M1 uses pglite, an in-process PostgreSQL-compatible database, through Drizzle ORM. This preserves PostgreSQL-shaped SQL semantics without requiring a separate database server in the bootstrap milestone.

The initial `tasks` table stores:

- `id`: text primary key containing an app-generated UUID v7.
- `user_id`: text owner field.
- `title`: required text.
- `created_at`: timezone-aware timestamp with database default `now()`.

`PGLITE_DATA_DIR` controls persistence:

- unset: in-memory mode for tests.
- local dev: `.pglite-dev` when configured.
- container runtime: `/var/lib/psykl/pglite` when Docker work lands.

### Authorization Boundary

M1 and M2 use a deliberately simple single-user auth posture. Every request must include `X-User-Id`; the global NestJS `UserIdGuard` rejects missing or malformed values and attaches the trimmed value to the request.

`user_id` ownership is the access model. There are no per-Task access control lists because PSYKL is single-user, multi-device, and never collaborative. Real authentication can replace the header source in M4 without changing the Task data model.

### Testing Strategy

The M1 service establishes the lower layers of the project test pyramid:

- Unit: pure service behavior such as UUID v7 generation and user-scoped query shape.
- Integration: Drizzle plus pglite schema and persistence behavior.
- Component: in-process HTTP contract tests for guard negative paths and Task endpoint positive paths.
- Static Analysis: ESLint, Prettier, and TypeScript scripts at package and recursive workspace levels.

End-to-end browser testing is planned for M1 Spec 5 after the PWA and Docker Compose stack exist.

## Architecture Decision Records

### ADR-M1-001: pnpm Workspace

Use pnpm and `pnpm-workspace.yaml` for the monorepo. pnpm aligns with the repository's lockfile convention, provides fast installs, and catches undeclared dependency bugs through strict dependency layout.

### ADR-M1-002: Shared Zod Contract Package

Use `packages/shared-types` as the schema source of truth. Zod schemas derive TypeScript types, service validation, and OpenAPI output. This avoids duplicating contracts between service and client code.

### ADR-M1-003: Strict Toolchain Pins

Pin Node 24 LTS and pnpm 10.x, and enforce engines through `.npmrc`. Install-time failures are preferable to runtime drift.

### ADR-M1-004: Generated Artifacts Are Rebuilt

Do not commit build outputs, OpenAPI output, or generated client API types. Package scripts and CI regenerate them from source schemas.

### ADR-M1-005: NestJS API Layer

Use NestJS for `service-task` because it keeps REST, GraphQL, and gRPC transport options open behind a shared service layer.

### ADR-M1-006: Schema-First API Discipline Via Zod

Use Zod schemas plus `nestjs-zod` and `zod-to-openapi` rather than hand-written OpenAPI or `@nestjs/swagger`. Consumers see an emitted OpenAPI contract, while source control preserves one schema source.

### ADR-M1-007: pglite With Drizzle ORM

Use pglite in M1 to get PostgreSQL-shaped semantics without a networked database server. Use Drizzle ORM and checked-in SQL migrations for schema management.

### ADR-M1-008: UUID v7 Task IDs

Generate Task IDs app-side as UUID v7 and store them in a text column. Time-ordered IDs support index locality and future offline-first client generation.

### ADR-M1-009: Global UserIdGuard

Use a global NestJS guard as the M1/M2 authorization boundary. It enforces `X-User-Id` and keeps route handlers from silently bypassing ownership checks.

### ADR-M1-010: Root Static Analysis Configuration

Use root ESLint flat config and Prettier config for TypeScript workspace packages. Package scripts invoke shared configuration to make recursive CI checks deterministic.
